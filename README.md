> 2. KVM源码阅读：先学习虚拟化源码，之后扩展到嵌套虚拟化源码的学习
>
>    （1）虚拟化
>
>    CPU 虚拟化 → 内存虚拟化 → 中断虚拟化 → I/O 虚拟化
>
>    > 在 KVM 的源码与设计中，CPU、内存、中断这三者的虚拟化核心机制主要在内核态的 KVM 模块中实现；而 I/O 虚拟化则是一个跨内核与用户态的协作过程，大量设备模拟逻辑实际上由用户态的 QEMU 承担。
>
>    ① CPU 虚拟化：VMX 指令集+VMCS（虚拟机控制结构） + vCPU 运行循环（搞清楚一个 vCPU 如何进入 Guest、因何退出、如何回到 KVM）
>
>    - 先抓住主线：`KVM_RUN` → `vcpu_enter_guest()` → `vmx_vcpu_run()` → VM-Exit → `handle_exit()` / `vmx_handle_exit()` → 处理后再进入 Guest。
>    - 重点理解：VMCS 的 guest/host 状态区、VM-Entry/VM-Exit 控制、退出原因分发、敏感指令拦截与模拟。
>
>    ② 内存虚拟化：地址翻译+建立映射+EPT 缺页
>
>    > EPT（扩展页表）
>
>    - GPA→HPA 的映射如何建立、缺页如何触发 VM-Exit、KVM 如何填充 EPT、什么时候需要 `mmu_notifier` 失效处理。
>    - 关注 TDP MMU 与影子页表两条路径的区别，Intel 平台上重点看 EPT violation 处理。
>
>    ③ 中断虚拟化：中断注入与投递过程
>
>    > APICv（高级可编程中断控制器虚拟化）
>
>    - 目标：理解外部中断、IPI、定时器中断如何被注入 Guest，以及 APICv 如何减少退出。
>
>    ④ I/O 虚拟化：设备发现 + PIO/MMIO 拦截 + 退出处理 + 设备模拟
>
>    - 这里要特别注意：“设备发现”主要不是 KVM 内核做的，而是 QEMU/ACPI/PCI 枚举等用户态或 Guest 侧机制；KVM 内核侧核心是拦截 PIO/MMIO、产生 VM-Exit、分发处理。
>    - 重点理解：一次 Guest 设备访问如何从 `handle_io()` / MMIO 退出走到 QEMU 设备模型，模拟完成后再返回 Guest；设备直通则涉及 VT-d/IOMMU 与 VFIO。
>
>    （2）嵌套虚拟化：
>
>    > 先学习虚拟化源码，之后扩展到嵌套虚拟化源码的学习
>
>    ① 核心心智模型：一切围绕 `is_guest_mode()`
>
>    理解嵌套虚拟化的第一把钥匙，是 `is_guest_mode(vcpu)` 这个判断。它通过 `HF_GUEST_MASK` 标志位，标识当前物理 CPU 是否正在代替 L1 执行 L2。
>
>    - 如果 `is_guest_mode()` 为假：L0 直接在执行 L1 的代码（比如 L1 的用户态程序），走的是你熟悉的普通单层退出处理路径。
>    - 如果 `is_guest_mode()` 为真：L0 正在执行 L2。此时 L0 不会去区分这是第几层嵌套，只要看到这个标志，就知道当前处于嵌套上下文中，需要特殊处理。
>
>    ② 两个 VMCS：`vmcs12` 与 `vmcs02`
>
>    嵌套虚拟化涉及两套关键的控制结构：
>
>    1. `vmcs12`（软件定义）：这是 L1 为其 L2 准备的 VMCS。L1 通过 `VMPTRLD` 等指令加载它，里面写满了 L1 希望 L2 看到的 CPU 状态和控制条件。
>    2. `vmcs02`（硬件使用）：这是 L0 真正加载到物理 CPU 上的 VMCS。物理硬件不认识 `vmcs12`，KVM 必须通过 `prepare_vmcs02()` 函数，将 `vmcs12` 的内容与 L0 自身的需求（`vmcs01`）进行“合并”，生成一份硬件可用的 `vmcs02`。L2 执行期间，`vmcs02` 是活跃的。
>
>    ③ 入口与退出：嵌套的执行流
>
>    - 入口（L1 → L2）：当 L1 执行 `VMLAUNCH` 或 `VMRESUME` 试图启动 L2 时，会触发 VM-Exit 到 L0。L0 捕获后，会调用 `nested_vmx_run()`，进而通过 `nested_vmx_enter_non_root_mode()` 完成状态切换并加载 `vmcs02`，正式开始执行 L2。
>    - 退出（L2 → ?）：L2 执行中产生 VM-Exit 时，物理 CPU 总是先退出到 L0。此时 KVM 的核心决策函数 `nested_vmx_exit_handled()` 会依据 `vmcs12` 中 L1 设定的退出控制位（Exit Control），逐项判断：
>      - L0 自行处理：如果导致退出的原因在 `vmcs12` 中没有被设置为“需要退出到 L1”（例如，L1 没有要求拦截 `HLT` 指令），L0 就直接模拟处理，然后通过 `nested_vmx_enter_non_root_mode()` 返回 L2 继续执行。
>      - 反射给 L1：如果该退出原因被 `vmcs12` 标记为需要 L1 处理（例如，L1 设置了拦截 `CPUID` 或 `I/O` 指令），L0 就执行 `nested_vmx_vmexit()`，将退出信息同步回 `vmcs12`，然后切换回 `vmcs01`，让 L1 的代码去处理这个退出。
>
>    值得注意的是，VMX 指令（如 `VMCALL`、`VMLAUNCH` 等）自身会无条件触发退出并交还给 L1，这是实现多层嵌套（如 L3）的基础。
>
>    ④ 性能关键：VMCS Shadowing
>
>    如果 L1 中有大量 `VMREAD`/`VMWRITE` 操作（在嵌套环境中很常见），每一次都会陷入 L0，开销巨大。VMCS Shadowing 是 Intel 提供的硬件加速特性，它允许 L0 配置物理 CPU，使得 L1 对 `vmcs12` 中部分字段的读写直接在硬件层面完成，而不会触发 VM-Exit 到 L0。相关补丁数据显示，这可以减少高达 40% 的嵌套虚拟化开销。在 KVM 中，这对应着 `shadow_vmcs` 的分配、字段位图以及 `sync_shadow_vmcs` 等同步机制。
